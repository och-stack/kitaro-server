KITARO API Documentation

KITARO is a Malaysian waste management and recycling information platform. This backend provides API services for user authentication, profile management, waste reporting, postcode lookup, administrative management and waste analytics.

1. API Overview

  • Backend: Node.js and Express.js
  • Database: Supabase PostgreSQL
  • Authentication: Supabase Authentication
  • External API: Countries.dev
  • Response Format: JSON
  • Content-Type: application/json

Base URL:

https://kitaro-server-indol.vercel.app

Authentication Header:

Authorization: Bearer YOUR_ACCESS_TOKEN

Protected endpoints require a valid Supabase access token. Include the token in the Authorization header.

3. Health Check API

GET /api/health

Purpose:

Checks whether the KITARO Express backend server is running and responding to requests.

Authentication: Not required.

Successful response (200):

{
    "success": true,
    "message": "KITARO API is running"
}

GET /api/health/supabase

Purpose:

Checks whether the backend can successfully query the Supabase PostgreSQL database.

Authentication: Not required.

Successful response (200):

{
    "success": true,
    "message": "Supabase connection is working"
}

Database connection failure (503):

{
    "success": false,
    "message": "Supabase is unavailable"
}

4. Authentication API

POST /api/auth/signup

Purpose:

Registers a new KITARO user using Supabase Authentication. The user account is created with email, password and display name.

Authentication: Not required.

Request body:

{
    "email": "user@example.com",
    "password": "password123",
    "display_name": "John"
}

Validation requirements:

  • Email, password and display name are required.
  • Email must have a valid basic email format.
  • Password must contain at least 8 characters.
  • Display name cannot be empty.
  • Email is converted to lowercase before registration.
  • Display name is trimmed before registration.

Successful response (201):

{
    "success": true,
    "message": "Account created successfully",
    "user": {
        "id": "USER_UUID",
        "email": "user@example.com"
    },
    "access_token": "ACCESS_TOKEN",
    "refresh_token": "REFRESH_TOKEN"
}

If email confirmation is enabled and Supabase does not return a session, the message will be: "Account created. Check your email to confirm your account."

In this case, access_token and refresh_token are null.

Possible errors:

  • 400: Email, password and display name are required.
  • 400: Please enter a valid email address.
  • 400: Password must be at least 8 characters.
  • 400: Supabase registration error.
  • 500: Unable to create account.

POST /api/auth/login

Purpose:

Authenticates an existing user using their email address and password.

Authentication: Not required.

Request body:

{
    "email": "user@example.com",
    "password": "password123"
}

Successful response (200):

{
    "success": true,
    "message": "Login successful",
    "user": {
        "id": "USER_UUID",
        "email": "user@example.com"
    },
    "access_token": "ACCESS_TOKEN",
    "refresh_token": "REFRESH_TOKEN"
}

Possible errors:

  • 400: Email and password are required.
  • 401: Unable to sign in with these credentials.
  • 500: Unable to sign in.

GET /api/auth/me

Purpose:

Retrieves the basic account information of the currently authenticated user.

Authentication: Required.

Successful response (200):

{
    "success": true,
    "user": {
        "id": "USER_UUID",
        "email": "user@example.com"
    }
}

Possible errors:

  • 401: Missing or invalid authentication token.

5. User Profile API

GET /api/profile

Purpose:

Retrieves the authenticated user's profile information from the kitaro_users table.

Authentication: Required.

Successful response (200):

{
    "success": true,
    "profile": {
        "id": "USER_UUID",
        "display_name": "John",
        "user_type": "resident",
        "postal_code": "48000",
        "matched_area": "Rawang, Selangor",
        "created_at": "TIMESTAMP",
        "updated_at": "TIMESTAMP"
    }
}

Possible errors:

  • 401: Authentication required.
  • 404: Profile not found.
  • 500: Unable to retrieve profile.

PATCH /api/profile

Purpose:

Updates permitted profile information for the authenticated user.

Authentication: Required.

Request body:

{
    "display_name": "John Tan",
    "user_type": "small_business",
    "postal_code": "48000"
}

Permitted fields:

  • display_name: Non-empty string.
  • user_type: resident or small_business.
  • postal_code: Five-digit Malaysian postcode or null.

Additional validation:

  • At least one valid field must be supplied.
  • Empty display names are rejected.
  • Invalid user types are rejected.
  • Invalid postcodes are rejected.
  • Changing postal_code clears matched_area.
  • updated_at is automatically updated.

Successful response (200):

{
    "success": true,
    "message": "Profile updated successfully",
    "profile": {
        "id": "USER_UUID",
        "display_name": "John Tan",
        "user_type": "small_business",
        "postal_code": "48000",
        "matched_area": null,
        "updated_at": "TIMESTAMP"
    }
}

Possible errors:

  • 400: Display name must not be empty.
  • 400: User type must be resident or small_business.
  • 400: Enter a valid 5-digit Malaysian postcode.
  • 400: Provide at least one valid field to update.
  • 401: Authentication required.
  • 500: Unable to update profile.

6. Postcode Lookup API

POST /api/postcode/lookup

Purpose:

Looks up a Malaysian postcode using Countries.dev, retrieves the matching area and saves the postcode and matched area to the authenticated user's profile.

Authentication: Required.

External API:

https://countries.dev/postal/MY/{postcode}

Request body:

{
    "postal_code": "48000"
}

Processing:

  1. Validates the five-digit Malaysian postcode.
  2. Sends a request to Countries.dev.
  3. Retrieves the first matching place.
  4. Combines the place name and state information.
  5. Updates postal_code and matched_area in kitaro_users.

Successful response (200):

{
    "success": true,
    "message": "Postcode matched successfully",
    "profile": {
        "id": "USER_UUID",
        "postal_code": "48000",
        "matched_area": "AREA, STATE"
    }
}

Possible errors:

  • 400: Enter a valid 5-digit Malaysian postcode.
  • 401: Authentication required.
  • 404: Postcode not found.
  • 404: No area information found for this postcode.
  • 502: Postcode lookup service is unavailable.
  • 500: Unable to look up postcode.

7. Waste Records API

Waste reports are stored in the kitaro_waste_records table. Each authenticated user can manage their own waste reports.

POST /api/waste-records

Purpose: Submits a new waste report.

Authentication: Required.

Request body:

{
    "waste_type": "Plastic",
    "waste_weight": 5.5,
    "area": "Rawang, Selangor",
    "description": "Plastic bottles collected"
}

Accepted waste types:

  • General / Residual Waste & Food Waste
  • Paper & Cardboard
  • Plastic
  • Glass
  • Metal
  • Electronic Waste (E-waste)

Validation requirements:

  • Waste type must match an accepted category.
  • Area is required and cannot be empty.
  • Description is required and cannot be empty.
  • Waste weight is optional.
  • If supplied, waste weight must be a positive number.
  • User ID is obtained from the authenticated session.
  • The initial status is determined by the database default.

Successful response (201):

{
    "success": true,
    "message": "Waste report submitted successfully",
    "report": {
        "id": "REPORT_UUID",
        "user_id": "USER_UUID",
        "waste_type": "Plastic",
        "waste_weight": 5.5,
        "area": "Rawang, Selangor",
        "description": "Plastic bottles collected",
        "status": "Submitted",
        "created_at": "TIMESTAMP"
    }
}

The report object includes the database-returned fields.

Possible errors:

  • 400: Valid waste type, area and description are required.
  • 400: Waste weight must be a positive number.
  • 401: Authentication required.
  • 500: Unable to submit waste report.

GET /api/waste-records

Purpose:

Retrieves all waste reports belonging to the authenticated user.

Authentication: Required.

Successful response (200):

{
    "success": true,
    "reports": [
        {
            "id": "REPORT_UUID",
            "user_id": "USER_UUID",
            "waste_type": "Plastic",
            "waste_weight": 5.5,
            "area": "Rawang, Selangor",
            "description": "Plastic bottles collected",
            "status": "Submitted",
            "created_at": "TIMESTAMP"
        }
    ]
}

Reports are sorted by created_at in descending order. The newest reports appear first.

Possible errors:

  • 401: Authentication required.
  • 500: Unable to retrieve waste reports.

GET /api/waste-records/:id

Purpose:

Retrieves one waste report belonging to the authenticated user.

Authentication: Required.

Path parameter:

  • id: Valid UUID of the waste report.

Successful response (200):

{
    "success": true,
    "report": {
        "id": "REPORT_UUID",
        "user_id": "USER_UUID",
        "waste_type": "Plastic",
        "waste_weight": 5.5,
        "area": "Rawang, Selangor",
        "description": "Plastic bottles collected",
        "status": "Submitted"
    }
}

Possible errors:

  • 400: Invalid UUID format, if rejected by validateUUID middleware.
  • 401: Authentication required.
  • 404: Waste report not found or not owned by the user.
  • 500: Unable to retrieve waste report.

DELETE /api/waste-records/:id

Purpose:

Deletes the authenticated user's own waste report, but only when its current status is Submitted.

Authentication: Required.

Path parameter:

  • id: Valid UUID of the waste report.

Successful response (200):

{
    "success": true,
    "message": "Waste report deleted successfully"
}

Possible errors:

  • 400: Invalid UUID format, if rejected by validateUUID middleware.
  • 401: Authentication required.
  • 404: Waste report not found or can no longer be deleted.
  • 500: Unable to delete waste report.

8. Admin Waste Records API

Administrative endpoints allow authorized administrators to review all waste reports and update their statuses.

Authentication: Required.

Authorization: Administrator access required.

GET /api/admin/waste-records

Purpose:

Retrieves all waste reports for administrative review, including the associated user's display name.

Successful response (200):

{
    "success": true,
    "reports": [
        {
            "id": "REPORT_UUID",
            "user_id": "USER_UUID",
            "waste_type": "Plastic",
            "status": "Submitted",
            "user": {
                "display_name": "John"
            }
        }
    ]
}

Each report also includes other fields returned by the database. Reports are sorted newest first.

Possible errors:

  • 401: Authentication required.
  • 403: Administrator permission required.
  • 500: Unable to retrieve waste reports.

PATCH /api/admin/waste-records/:id/status

Purpose:

Updates the status of an existing waste report. Only authorized administrators can perform this operation.

Path parameter:

  • id: Valid UUID of the waste report.

Request body:

{
    "status": "Resolved"
}

Accepted statuses:

  • Submitted
  • Going
  • Resolved

Automatic database updates:

  • last_edited_by: Authenticated administrator's user ID.
  • updated_at: Current timestamp.
  • resolved_at: Current timestamp when status is Resolved.
  • resolved_at: Set to null for other statuses.

Successful response (200):

{
    "success": true,
    "message": "Waste record status updated successfully",
    "report": {
        "id": "REPORT_UUID",
        "status": "Resolved",
        "last_edited_by": "ADMIN_UUID",
        "updated_at": "TIMESTAMP",
        "resolved_at": "TIMESTAMP"
    }
}

Possible errors:

  • 400: Invalid report status.
  • 400: Invalid UUID format, if rejected by validateUUID middleware.
  • 401: Authentication required.
  • 403: Administrator permission required.
  • 404: Waste report not found.
  • 500: Unable to update report status.

Note: The current admin API supports status updates only. Editing other report fields is not implemented in this route. The Rejected status is also not currently accepted.

9. Waste Analytics API

The analytics endpoints retrieve aggregated waste reporting information using PostgreSQL functions in Supabase.

Authentication: Required.

Authorization: Authenticated users.

GET /api/analytics/hotspots

Purpose: Waste Hotspot Analysis.

Identifies areas with higher waste reporting activity using the kitaro_analytics_hotspots database function.

Successful response (200):

{
    "success": true,
    "analytics": [
        {
            "area": "AREA",
            "report_count": 10
        }
    ]
}

Example structure only. Actual fields depend on the PostgreSQL function's returned columns.

GET /api/analytics/composition

Purpose: Waste Composition Analysis.

Summarises waste types, report counts and total waste weight using the kitaro_analytics_composition database function.

Successful response (200):

{
    "success": true,
    "analytics": [
        {
            "waste_type": "Plastic",
            "report_count": 10,
            "total_weight": 50
        }
    ]
}

The returned fields represent waste type, report count and total recorded waste weight.

GET /api/analytics/trends

Purpose: Waste Reporting Trend Analysis.

Analyses waste reporting activity over time using the kitaro_analytics_trends database function.

Successful response (200):

{
    "success": true,
    "analytics": [
        {
            "period": "EXAMPLE_PERIOD",
            "report_count": 10
        }
    ]
}

Example structure only. Actual fields depend on the PostgreSQL function's returned columns.

Possible errors for all analytics endpoints:

  • 401: Authentication required.
  • 500: Unable to calculate the requested analytics.

10. Middleware and Security

authenticateUser.js

Verifies the Supabase access token and identifies the authenticated user before allowing access to protected API operations.

adminOnly.js

Checks administrator authorization before allowing access to administrative waste record operations.

validateUUID.js

Validates UUID parameters for individual waste record endpoints before processing the request.

errorHandler.js

Provides centralized error handling for errors passed to the Express error-handling middleware. Individual route handlers also handle their own errors.

Data Security

  • Protected endpoints require authentication.
  • Users can only retrieve their own waste reports.
  • Users can only delete their own Submitted reports.
  • Administrator endpoints require admin authorization.
  • UUID parameters are validated before processing.
  • Profile updates are restricted to permitted fields.
  • Admin status updates record the administrator's user ID.

14. KITARO API Summary

KITARO provides backend services to support waste reporting, user management, administrative workflows and waste data analysis.

The backend uses Express.js to manage API requests, Supabase PostgreSQL to store and analyse data, and Supabase Authentication to secure user access.

The modular backend structure separates route handling, authentication, authorization, validation and database operations to support maintainability and code organisation.
