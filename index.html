KITARO API Documentation

1. API Overview

KITARO is a Malaysian waste-management platform that allows users to submit waste reports, manage their profiles and view waste analytics.

The backend is built using Node.js and Express.js, with Supabase providing authentication and PostgreSQL database services.

Base URL

https://kitaro-server-indol.vercel.app

Authentication

Protected endpoints require a valid Supabase access token. Include the token in the Authorization header: 

Authorization: Bearer YOUR_ACCESS_TOKEN

Content Type

Content-Type: application/json

2. Backend NPM Packages

The following NPM packages are used by the KITARO backend.

Package Installation Command Purpose
Express npm install express Creates the backend server, API routes and middleware.
Supabase JS npm install @supabase/supabase-js Connects to Supabase Authentication and PostgreSQL.
CORS npm install cors Allows frontend and backend cross-origin communication.
Dotenv npm install dotenv Loads environment variables from the .env file.

Install All Packages

npm install express @supabase/supabase-js cors dotenv

Note: Node.js built-in modules such as path and the built-in fetch do not require separate NPM installation. Nodemon is optional and can be installed for automatic server restarts during development.

5. Authentication API

5.1 Register a New User

POST /api/auth/signup

Registers a new user through Supabase Authentication. The endpoint validates the submitted information before creating the account.

Request Body

{
    "email": "user@example.com",
    "password": "Password123",
    "display_name": "John",
    "user_type": "resident"
}

Required Fields

  • email: Must be a non-empty string with a valid email format.
  • password: Must be a non-empty string with at least 8 characters.
  • display_name: Must be a non-empty string.
  • user_type: Must be either resident or small_business.

Validation and Data Handling

  • Checks that all required fields are provided as strings.
  • Trims whitespace from the email and display name.
  • Converts the email address to lowercase.
  • Checks the email format using basic character-position validation.
  • Checks that the password contains at least 8 characters.
  • Stores the display name and user type in Supabase Auth user metadata.

Successful Response — 201 Created

{
    "success": true,
    "message": "Account created successfully",
    "user": {
        "id": "USER_UUID",
        "email": "user@example.com"
    },
    "access_token": "ACCESS_TOKEN",
    "refresh_token": "REFRESH_TOKEN"
}

The success message depends on whether Supabase returns an active session.

When an active session is returned:

"message": "Account created successfully"

When email confirmation is required:

"message": "Account created. Check your email to confirm your account."

When no active session is returned, the access and refresh tokens are null. The user object is also null if Supabase does not return a user.

Missing or Invalid Required Fields — 400 Bad Request

{
    "success": false,
    "message": "Email, password, and display name are required"
}

Invalid Email — 400 Bad Request

{
    "success": false,
    "message": "Please enter a valid email address"
}

Password Too Short — 400 Bad Request

{
    "success": false,
    "message": "Password must be at least 8 characters"
}

Supabase Signup Error — 400 Bad Request

{
    "success": false,
    "message": "SUPABASE_ERROR_MESSAGE",
    "code": "SUPABASE_ERROR_CODE"
}

Unexpected Server Error — 500 Internal Server Error

{
    "success": false,
    "message": "Unable to create account"
}

5.2 Sign In

POST /api/auth/login

Authenticates an existing user through Supabase signInWithPassword().

Request Body

{
    "email": "user@example.com",
    "password": "Password123"
}

Validation and Data Handling

  • Checks that email and password are non-empty strings.
  • Trims whitespace from the email address.
  • Converts the email address to lowercase.
  • Authenticates the user using Supabase.
  • Checks that Supabase returns both a user and an active session.

Successful Response — 200 OK

{
    "success": true,
    "message": "Login successful",
    "user": {
        "id": "USER_UUID",
        "email": "user@example.com"
    },
    "access_token": "ACCESS_TOKEN",
    "refresh_token": "REFRESH_TOKEN"
}

Missing Required Fields — 400 Bad Request

{
    "success": false,
    "message": "Email and password are required"
}

Invalid Login Credentials — 401 Unauthorized

{
    "success": false,
    "message": "Unable to sign in with these credentials"
}

Unexpected Server Error — 500 Internal Server Error

{
    "success": false,
    "message": "Unable to sign in"
}

5.3 Retrieve Authenticated User

GET /api/auth/me

Uses the authenticateUser middleware to verify the access token and retrieve the currently authenticated user's details.

Header

Authorization: Bearer YOUR_ACCESS_TOKEN

Successful Response — 200 OK

{
    "success": true,
    "user": {
        "id": "USER_UUID",
        "email": "user@example.com"
    }
}

6. User Profile API

6.1 Retrieve User Profile

GET /api/profile

Retrieves the authenticated user's profile from kitaro_users.

Header

Authorization: Bearer YOUR_ACCESS_TOKEN

Successful Response — 200 OK

{
    "success": true,
    "profile": {
        "id": "USER_UUID",
        "display_name": "John",
        "user_type": "resident",
        "postal_code": "48000",
        "matched_area": "Rawang",
        "created_at": "2026-01-01T00:00:00Z",
        "updated_at": "2026-01-01T00:00:00Z"
    }
}

The response fields are based on the profile query. Actual values depend on the user's saved profile.

6.2 Update User Profile

PATCH /api/profile

Updates the authenticated user's profile. Only the supported fields supplied in the request are updated.

Request Body

{
    "display_name": "John Tan",
    "user_type": "small_business",
    "postal_code": "48000"
}

Supported Fields

  • display_name: Non-empty display name.
  • user_type: resident or small_business.
  • postal_code: Five-digit Malaysian postcode or null.

When the postal code changes, the saved matched area is cleared until a new postcode lookup is performed.

Successful Response — 200 OK

{
    "success": true,
    "message": "Profile updated successfully"
}

Validation Error — 400 Bad Request

{
    "success": false,
    "message": "No valid profile fields provided"
}

7. Postcode Lookup API

7.1 Look Up Malaysian Postcode

POST /api/postcode/lookup

Uses the Countries.dev API to look up a Malaysian postcode. The returned area is saved in the authenticated user's profile.

Request Body

{
    "postal_code": "48000"
}

External API

https://countries.dev/postal/MY/{postcode}

The backend retrieves the place name and state information, then updates the user's postal_code and matched_area in kitaro_users.

Successful Response — 200 OK

{
    "success": true,
    "message": "Postcode lookup successful"
}

Validation Error — 400 Bad Request

{
    "success": false,
    "message": "Invalid Malaysian postcode"
}

Postcode Not Found — 404 Not Found

{
    "success": false,
    "message": "Postcode not found"
}

External Service Error — 502 Bad Gateway

{
    "success": false,
    "message": "Unable to retrieve postcode information"
}

8. Waste Records API

8.1 Submit a Waste Report

POST /api/waste-records

Allows an authenticated user to submit a new waste report. The user ID is obtained from the verified access token.

Request Body

{
    "waste_type": "Plastic",
    "waste_weight": 5,
    "area": "Rawang",
    "description": "Plastic bottles collected from the neighbourhood"
}

Supported Waste Types

  • General / Residual Waste & Food Waste
  • Paper & Cardboard
  • Plastic
  • Glass
  • Metal
  • Electronic Waste (E-waste)

Validation Rules

  • waste_type must match a supported waste type.
  • area must be a non-empty string.
  • description must be a non-empty string.
  • waste_weight is optional but must be a finite positive number when provided.

The report status is assigned using the database default. The user cannot submit a report on behalf of another user by supplying a different user ID.

Successful Response — 201 Created

{
    "success": true,
    "message": "Waste report submitted successfully",
    "record": {
        "id": "RECORD_UUID",
        "waste_type": "Plastic",
        "waste_weight": 5,
        "area": "Rawang",
        "description": "Plastic bottles collected from the neighbourhood",
        "status": "Submitted"
    }
}

8.2 Retrieve User Waste Reports

GET /api/waste-records

Retrieves waste reports belonging to the authenticated user. Records are ordered by creation date, newest first.

Successful Response — 200 OK

{
    "success": true,
    "records": [
        {
            "id": "RECORD_UUID",
            "waste_type": "Plastic",
            "area": "Rawang",
            "status": "Submitted",
            "created_at": "2026-01-01T00:00:00Z"
        }
    ]
}

8.3 Retrieve a Specific Waste Report

GET /api/waste-records/:id

Retrieves one waste report using its UUID. The endpoint checks that the report belongs to the authenticated user.

Example

GET /api/waste-records/RECORD_UUID

Successful Response — 200 OK

{
    "success": true,
    "record": {
        "id": "RECORD_UUID",
        "waste_type": "Plastic",
        "area": "Rawang",
        "description": "Plastic bottles collected",
        "status": "Submitted"
    }
}

Record Not Found — 404 Not Found

{
    "success": false,
    "message": "Waste report not found"
}

8.4 Delete a Waste Report

DELETE /api/waste-records/:id

Allows a user to delete their own waste report only when its status is Submitted.

Example

DELETE /api/waste-records/RECORD_UUID

Successful Response — 200 OK

{
    "success": true,
    "message": "Waste report deleted successfully"
}

Record Not Found or Not Eligible — 404 Not Found

{
    "success": false,
    "message": "Waste report not found or cannot be deleted"
}

9. Admin Waste Records API

These endpoints are restricted to authenticated administrators. The admin middleware checks whether the authenticated user has administrator access.

9.1 Retrieve All Waste Reports

GET /api/admin/waste-records

Retrieves all waste reports for administrative management. The query also retrieves the related user's display name.

Header

Authorization: Bearer ADMIN_ACCESS_TOKEN

Successful Response — 200 OK

{
    "success": true,
    "records": [
        {
            "id": "RECORD_UUID",
            "waste_type": "Plastic",
            "area": "Rawang",
            "status": "Submitted",
            "user": {
                "display_name": "John"
            }
        }
    ]
}

9.2 Update Waste Report Status

PATCH /api/admin/waste-records/:id/status

Allows an administrator to update the status of a waste report.

Request Body

{
    "status": "Going"
}

Allowed Status Values

  • Submitted
  • Going
  • Resolved

The endpoint also records the administrator who made the change and updates the report's timestamp. When the status becomes Resolved, the resolution timestamp is recorded.

Successful Response — 200 OK

{
    "success": true,
    "message": "Waste report status updated successfully"
}

Validation Error — 400 Bad Request

{
    "success": false,
    "message": "Invalid status"
}

Note: This endpoint updates the report status. It does not provide an endpoint for editing other waste report information.

10. Waste Analytics API

The analytics endpoints use PostgreSQL stored functions through Supabase RPC (Remote Procedure Call).

10.1 Waste Hotspot Analysis

GET /api/analytics/hotspots

Retrieves waste reporting information grouped by area to help identify waste hotspots.

Supabase RPC

kitaro_analytics_hotspots

Successful Response — 200 OK

{
    "success": true,
    "analytics": [
        {
            "area": "Rawang",
            "report_count": 10
        }
    ]
}

The response above is an illustrative example. Refer to the PostgreSQL function definition for the exact returned columns.

10.2 Waste Composition Analysis

GET /api/analytics/composition

Retrieves waste report counts and total waste weight grouped by waste type.

Supabase RPC

kitaro_analytics_composition

        {
            "waste_type": "Plastic",
            "report_count": 10,
            "total_weight": 25

The returned columns are waste_type, report_count and total_weight.

11. Middleware and Security

KITARO uses Express middleware to handle authentication, administrator authorization, input validation and errors.

11.1 authenticateUser

  • Reads the access token from the Authorization header.
  • Verifies the token with Supabase Authentication.
  • Attaches the authenticated user to the request.
  • Prevents unauthenticated access to protected endpoints.

11.2 adminOnly

  • Checks whether the authenticated user is an administrator.
  • Restricts administrator endpoints to authorized users.

11.3 validateUUID

  • Validates record IDs used in URL parameters.
  • Prevents invalid UUID values from reaching database queries.

11.4 errorHandler

  • Provides centralized handling for Express errors.
  • Helps return consistent error responses.

11.5 Supabase Security

  • Uses Supabase Authentication to verify user identity.
  • Uses the authenticated user's ID when accessing personal records.
  • Restricts waste report access to the report owner.
  • Uses administrator authorization for admin-only endpoints.
  • Stores environment variables outside the source code.

Do not publish actual credentials or commit the .env file to GitHub.

15. Testing the API

API endpoints can be tested using Postman or another HTTP client.

  1. Start the backend server.
  2. Test GET /api/health to check the API.
  3. Test GET /api/health/supabase to check the database connection.
  4. Register a user using POST /api/auth/signup.
  5. Sign in using POST /api/auth/login.
  6. Copy the access token from the login response.
  7. Add the token to the Authorization header for protected endpoints.
  8. Test the profile, postcode and waste record endpoints.
  9. Test administrator endpoints using an authorized admin account.
  10. Test analytics endpoints to retrieve database analysis results.

17. KITARO API Summary

The KITARO backend provides the following main capabilities:

  • Authentication: User registration, login and token verification through Supabase.
  • Profile Management: Retrieve and update user profile information.
  • Postcode Lookup: Retrieve Malaysian postcode area information through Countries.dev.
  • Waste Reporting: Submit, retrieve and delete eligible waste reports.
  • Administration: Retrieve all reports and update their statuses.
  • Waste Analytics: Analyse waste hotspots, waste composition and reporting trends using PostgreSQL functions.

The backend connects the KITARO frontend with Supabase Authentication, PostgreSQL database services and external postcode lookup services.
